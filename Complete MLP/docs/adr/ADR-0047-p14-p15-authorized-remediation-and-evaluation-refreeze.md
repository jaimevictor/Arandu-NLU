# ADR-0047: P14-P15 authorized remediation and evaluation refreeze

- Status: `ACCEPTED_AUTONOMOUS`
- Date: 2026-09-10
- Owners: P14-P15, FINAL

## Context

P15 stopped before candidate freeze at commit
`f8af02a8525e8c76c2be140ccf764964d5a4763e`, with exact governance
evidence later committed at
`d1190c37b1429bbc4a7cf69e019ede6af33fd0a6`.

The blocked checkpoint records four release-blocking classes:

1. the companion can authorize an effect after only an in-memory Home
   Assistant config-entry update, before the restart marker is durable;
2. a credential-bearing helper that resists termination can disappear from
   ownership, capacity, and shutdown accounting;
3. the first P15 evaluation lineage produced zero exact plan outcomes and was
   also invalidated by test-time reads of real release splits; and
4. native Linux amd64 and arm64 execution, real supported Home Assistant
   lifecycle execution, and warm end-to-end reference evidence are absent.

The existing P02-v1 held-out and performance bytes cannot support another
passing claim after behavior changes. P14's exceptional correction authority
and P15 convergence pass one were both exhausted or rejected. The user then
explicitly directed the executor to perform the requested reopening,
replacement evaluation lineage, remediation, and native qualification.

## Decision

`USR-045` supersedes only the terminal-stop branches of `USR-043`,
`USR-044`, and ADR-0045 for one integrated resumed P15 convergence pass. It
does not waive any safety, correctness, provenance, licensing, clean-room,
native-execution, real-runtime, performance, review, packaging, or terminal
requirement.

### Mandatory chronology

Before any behavior-affecting product or linguistic byte changes, the
executor must freeze one new Apache-2.0
`PROJECT_AUTHORED_SYNTHETIC` P02 qualification lineage in an immutable
commit. The lineage must:

- use a new source ID, corpus version, generator identity, case identities,
  family identities, and whole-artifact hashes;
- bind a versioned deterministic generator specification, generator source,
  expected typed semantics, split policy, and exact manifest;
- provide train, development, held-out, performance, and independent
  fail-closed suites;
- prove byte-for-byte regeneration, cross-split text, family, case,
  generator-record, and semantic-identity separation;
- identify the freeze as preceding the remediation implementation under
  test; and
- prohibit held-out and performance record access except through the sealed
  aggregate-only runner after the remediation candidate freezes.

The executor may use only eligible train, development, public contract,
technical fixture, and existing non-held-out evidence during remediation.
The old P02-v1 held-out and performance results remain historical failure
evidence and are permanently ineligible for the replacement release claim.

### Authorized remediation

After the replacement lineage freezes, one integrated correction may change
only what is required to:

- make the pre-effect restart barrier durably acknowledged before dispatch;
- retain ownership, capacity accounting, and shutdown authority for every
  helper until child exit is proved;
- correct the zero-plan root cause using eligible non-held-out evidence and
  generic deterministic behavior rather than held-out-specific rules;
- bind the sealed evaluator and P15 validator to the replacement lineage;
  and
- complete the already-selected P15 native build, real Home Assistant,
  performance, packaging, and source-reconciliation architecture.

P13 source, transport, dependency, protocol, and cryptographic selections
remain immutable except for release-only native target closure already owned
by P15. No cross-compilation, emulation, architecture relabeling, mock-only
lifecycle evidence, proprietary tool, or unadmitted service can substitute
for a required native or real-runtime result.

### Bounded pass and minimum acceptance

The resumed pre-candidate pass unit is one integrated approach comprising:

1. replacement-lineage freeze;
2. the four blocker-class corrections and their direct regressions;
3. exact P14 debt closure;
4. P15 native and real-runtime admission;
5. sealed semantic and performance qualification; and
6. deterministic release artifact production and reconciliation.

The pass succeeds only if:

- the complete P14 gate and six independent P14 debt roles pass one exact
  immutable baseline;
- the replacement P15 held-out, negative-suite, confidence, performance, and
  warm end-to-end gates pass without case-level release-split disclosure;
- both native Linux architectures and the real supported Home Assistant
  lifecycle pass on qualifying resources;
- every release byte is reproducible, licensed, source-reconciled, and
  represented in checksums, notices, manifest, and SPDX evidence;
- the complete P15 gate passes; and
- every mandatory P15 reviewer passes the same immutable candidate with no
  open P0 through P2 finding.

No P15 candidate round has yet been consumed. The first minimally acceptable
candidate checkpoints immediately. A failed resumed pre-candidate approach
or unavailable mandatory external resource returns P15 to `BLOCKED`; it does
not authorize weakened evidence or another implicit redesign.

## Consequences

- P15 may resume implementation only after the replacement corpus freeze.
- P14 behavior may be corrected within the exact inherited blocker scope.
- The original P15 aggregate remains auditable but cannot authorize tuning or
  release.
- Native and real Home Assistant resources remain mandatory external
  preconditions; authorization to use them is not evidence that they exist.
- P16 and FINAL remain queued until P15 passes.

## Rollback

Before behavior changes, discard an invalid replacement lineage and freeze a
corrected one within the same resumed pass. After behavior changes begin, any
replacement-lineage defect, release-split access violation, P0 through P2
finding, or unavailable mandatory native/runtime precondition stops P15 as
blocked for a new explicit user decision.
